# CAL-38：历史饮食、运动及快照修正

实现交接日期：2026-10-14。基于已完成的 CAL-37，不改称重编辑或计算公式。
当前开发里程碑为 v0.0.4；应用版本仍为 `0.0.3`，schema 仍为 `3`，
calculation version 仍为 `v2-simple-energy-kj-1`。本文不是发布或验收通过声明。

## 用户入口与三种饮食修正

首页 K 线选择日期 → 当日记录 → 对应饮食或运动行的「编辑」。沿用现有时间线，
不要求修改食品库来更正一条历史记录。饮食表单较长，字段区可滚动，保存/取消按钮在滚动区外。

| 模式 | 使用方式 | 保存含义 |
| --- | --- | --- |
| 普通份量修正（默认） | 修改份量、日期/时间、餐次、备注 | 只按 `新份量 / 旧份量` 缩放该事件已保存的能量和营养；不读取当前来源来重算 |
| 更换食品/食谱或单位 | 显式勾选后重新选择来源 | 按当前食品、命名份量或食谱计算一次，替换同一事件的来源与快照 |
| 手动修正历史总量 | 显式勾选「手动修正这条记录的热量 / 营养总量」 | 输入最终份量对应的整条事件总量，不是每 100g 数值，也不再自动按份量缩放 |

更换来源与手动快照模式互斥，应用适配器也拒绝同时提交两个模式。
来源替换不能与 CUSTOM 名称/单位修正组合；CUSTOM 不能改造成食品/食谱关联事件。
普通 FOOD/RECIPE 修正不能直接修改名称或单位：这些字段属于保存的来源信息。
`IntakeSnapshotEdit` / `CustomIntakeEdit` 是共享的类型化修正对象，Qt 不执行 SQL。

例如：原记录 250g / 1000kJ，默认改为 25g 得到 100kJ，不受后来的食品库改动影响。
若勾选手动修正并填写 25g / 150kJ，则保存 150kJ，而不是再乘以 25/250。
以后普通改为 50g，会基于这次手动修正后的 150kJ 得到 300kJ。

## CUSTOM 与历史来源

- CUSTOM 编辑显示原记录的名称、份量、单位、餐次、时间、备注、能量和四项营养。
  名称/单位必须非空白；能量/营养需要开启手动快照模式才能修改。
- CUSTOM 名称/单位只影响所选事件；始终保留 `source_type='CUSTOM'` 和原有空 `source_id`。
  普通份量修正仍按原快照缩放，单位文本修正本身不推断新的换算关系。
- FOOD/RECIPE 手动快照修正保留原来源 ID、类型、名称及单位，表示记录最初的来源。
  保存的能量/营养现在是用户明确修正的历史事实，不承诺与今天的来源库一致。
- 食品/食谱/运动类型已软删除或修改，不妨碍普通修正；显式替换必须选择可用来源。
- 所有修正均为原行更新，保留事件 `id`、`created_at` 和无关字段，不新增重复事件。
  不写食品、食谱、份量、运动类型库，也不直接修改称重或资料作为校准输入。

## 单位、精度与时间

- 食品 g/ml 保留各自维度；命名份量替换沿用当前份量到基础单位的既有换算。
  普通编辑不重新读取命名份量的换算值。
- 已存食谱 `unit='recipe', amount=0.5` 显示为 0.5 份食谱（整份的 50%）。
  普通改为 0.25 就是四分之一份；不能再除以 100。
- 只有显式来源替换的 `ratio_percent=50` 会转为存储 `amount=0.5`。
  混合 g/ml 食谱仍只支持比例，不引入密度推断。
- 复用 `PreciseDoubleSpinBox`、`EnergySpinBox`、`OptionalNutrientEditor`。
  显示两位小数不代表重新量化原值。能量始终存 canonical kJ，kJ/kcal 切换保持未改值的精度。
- 编辑器显示原事件的本地钟面。未改时间时传回原 datetime，服务保留数据库中原有
  offset、`Z`、空格/`T`、小数秒及 `local_date` 文本；真正改时间才使用现有本地秒精度规范化。
- 未修改的 SQL NULL 备注仍为 NULL；非空备注改为空文本可正常清空。
  应用/服务按最终字段比较识别无变化，不改 `updated_at`，不标脏、不触发重算。
- 运动编辑保留小数时长、旧零值及已保存类型名称；类型替换是显式选项，不携带库默认能量覆盖原事件。
  `active_kj` 仍代表静息之外的额外活动消耗。

## 营养：未知不是零

手动模式明确显示蛋白质、膳食纤维、脂肪、碳水化合物四项的「已知」选择。
未勾选存 canonical NULL，已勾选并输入 0 才表示已知为零。

普通修正遵循以下规则：

- 份量不变时，不写任何营养字段，也不进行乘以 1 的往返。
- 份量变化时，分别缩放已保存的能量、旧非空营养列、canonical 已知值；canonical NULL 保持 NULL。
- 保留原来的 `nutrition_complete` 三态，包括 legacy NULL 以及显式 0，不推断数据已完整。

手动快照修正遵循以下规则：

- 若四项有效营养值与 `intake_contribution()` 读取值完全相同，保留原始营养列和完整性标记。
  因此仅勾选模式、切换能量显示单位、只更正能量，都不会顺便迁移 legacy NULL 或把 0 标记提升为完整。
- 若用户确实改变了四项中的任意一项，保存整个明确提交的已知/未知向量。
  四项都已知才设 `nutrition_complete=1`，否则设 0。
- 旧 `*_snapshot` 列不能存 NULL：未知项在这些旧列中使用 0 占位，canonical 列保持 NULL，
  同时 `nutrition_complete=0`，现有读取逻辑不会把这些占位值当作已知零。
- 未修改 `app/nutrition.py` 的一般读取语义，也没有扫描、自动修复或迁移其他历史记录。

## 原子性、日期边界与失败恢复

1. 适配器检查互斥模式、活动记录和改日边界；服务检查有限数值、正份量、非负能量/营养、
   合法餐次、CUSTOM 名称/单位及活动来源。
2. 复用既有 Database 单写入者租约和 `BEGIN IMMEDIATE` 事务。
   所选事件 UPDATE 与 `mark_dirty(min(old_day, new_day))` 使用同一连接、同一事务。
   SQL 更新失败或失效标记失败时，事实、缓存标记和 dirty 起点一起回滚；不调用后续重算。
3. 有实际变化才提交事实并重算。重算终点覆盖旧日、新日、今天，以及已有缓存的最晚日期，
   使跨日营养、能量、树图、K 线、预测和既有校准派生结果刷新。
4. 编辑成功且有实际变化时，时间线刷新并发出 `data_changed`，供首页刷新。
   取消、无变化保存、验证/写入失败都不发成功变化信号。

日期边界使用记录本地日，不转换到 UTC。有资料/模型时，跨日目标不能早于
`max(最早 effective profile revision 日, 最早活动实际称重日)`；资料或称重缺失时拒绝改日，
提示先恢复数据。拒绝移动到 `9999-12-31`，避免现有每日迭代越界。
没有任何资料、revision 或称重的纯事实库仍可编辑（服务/合成 fixture 可用）；没有新增 90 天截断。
既有早期记录的同日更正不被这个「改日」边界阻止。CAL-37 的称重边界实现不变。

事实写入与派生计算是两个阶段，不把整个计算过程塞入事件写事务：

- **验证/写入失败**：没有提交，原记录和派生缓存状态不变，窗口保持可编辑，可直接修正后再保存。
- **事实已提交、派生重算失败**：不伪称事实已回滚。抛出 `RecordRecalculationError`，携带最新保存的 DTO；
  窗口明确显示「记录已保存，图表待刷新」，不发成功变化信号，使用已提交值重置表单和模式。
  dirty 范围保留用于既有重算恢复流程。关闭编辑后刷新首页可以重试派生计算；也可继续修改已保存事实。
  仅无变化保存不会清除 dirty 或代替刷新操作。
