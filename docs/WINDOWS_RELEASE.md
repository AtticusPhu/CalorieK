# CalorieK v0.0.4：Windows 使用与发布流程

面向 Windows 10/11 x64 用户。应用本地、离线运行；打包版不需要安装 Python。

## 发布状态与版本标识

已发布的 v0.0.3 是此前 Windows 基线，其发布基线已完成 CAL-13、CAL-14、CAL-16 独立验证与长历史性能验证。当前源码为 **v0.0.4 发布准备状态**，包含已通过独立审查和用户 Windows 验证的 CAL-37 / CAL-38 修正功能；这不等于 v0.0.4 Windows Release 已发布。下载以 [GitHub Releases](https://github.com/AtticusPhu/CalorieK/releases) 中的实际资产为准。

当前源码元数据为 `APP_VERSION=0.0.4`、`SCHEMA_VERSION=3`、`CALCULATION_VERSION=v2-simple-energy-kj-1`。v0.0.4 不增加 schema 世代、不改变能量/体重公式或派生计算版本。CAL-12、CAL-37、CAL-38 等历史交接文档保留其实现当时的版本和执行状态，不能代替本次元数据调整与最终 Release 的验证。

修改源码版本不会更新已有 `dist` 目录或下载的 EXE；任何仍显示 `0.0.3` 的构建都不是 v0.0.4 发布包，不能通过改 ZIP 名称替代重新构建与验证。v0.0.4 由 [CAL-41](https://linear.app/atticum/issue/CAL-41/validate-and-publish-caloriek-v004-windows-release) 专用发布关卡把关。

## 下载与首次启动

1. 在实际已发布版本的 Release Assets 中下载对应 Windows x64 ZIP；下述 v0.0.4 功能需要正式的 v0.0.4 包。若尚无该资产，旧 v0.0.3 包不包含这些增强。`Source code (zip)` 不是打包应用；旧版 v0.0.1 不包含每日营养卡片。
2. 解压全部内容，保留 `CalorieK` 文件夹的完整结构，包括 `CalorieK.exe`、`_internal` 及其他随包文件。不要在 ZIP 内直接运行，也不要将 EXE 单独拖出。
3. 双击 `CalorieK.exe`，按向导填写个人资料和当前实际体重。之后从首页记录饮食、运动和称重。
4. 在“设置与数据”中选择 kJ 或 kcal 并保存。新用户、从旧库升级的用户默认使用 kJ；切换只改变显示/输入单位。

若 Windows 提示未知发布者或阻止启动，先核对下载来源及该 Release 提供的校验信息；不要关闭系统安全保护或下载来历不明的 DLL。程序启动失败时先保留错误提示，按下方排查。

## v0.0.4 新功能：更正已有记录

从首页 K 线选择日期，在每日时间线对应行点击「编辑」。

- **称重**：修正实际体重、日期/时间、`AUTO / OPEN / CLOSE` 锚点及备注，仍是同一条测量。首次建档称重也可更正，但不会同时改写历史个人资料版本。
- **普通饮食份量更正**：默认按原来保存的快照同比例缩放。例如 250g / 1000kJ 改为 25g，保存为 100kJ；后来改名、改营养或停用来源食品不会改变该规则。
- **显式更换来源/单位**：勾选「更换食品 / 食谱或单位」，重新选择可用来源，按当前库值保存一次新快照，仍保留原事件 ID 与创建时间。
- **显式修正历史总量**：勾选「手动修正这条记录的热量 / 营养总量」，填写最终份量对应的整条记录总量，不是每 100g 数值，也不会再按份量缩放。此模式与更换来源互斥，只改选中事件，不改库或其他历史。
- **CUSTOM**：可以改名称、份量、非空单位、餐次、时间及备注；总能量和四项营养通过手动模式修改。未勾选营养「已知」为未知，勾选并输入 0 才是已知零；记录仍无食品库关联。
- **食谱与运动**：已存 0.5 份食谱等于整份的 50%，普通改为 0.25 就是四分之一份；只有显式比例替换才把输入的 50% 转为 0.5。运动可修正时长、额外消耗、时间、备注，并显式替换运动项目，普通编辑保留已存名称和数值。

未修改的原值保留精度及时间文本，切换 kJ/kcal 不把两位小数显示写回原始数据。取消/无变化保存不改记录或缓存。有实际变化时按受影响日期重算营养、Treemap、K 线、预测和校准，再刷新界面。

## v0.0.4 已知边界与失败提示

- 本次只补齐历史称重、饮食、运动及摄入快照修正；未新增任意历史资料版本编辑，也未新增这些历史记录的删除/恢复 UI，不表示所有用户数据类型都可编辑。
- 称重跨日目标不能早于最早资料生效日；有资料/模型时，饮食/运动目标不能早于最早资料生效日和最早活动实际称重日中的较晚者。缺少所需资料/称重锚点、目标越界或移动到 `9999-12-31` 时会在写入前拒绝；请按提示选择支持的日期，不要手改数据库绕过保护。
- 未新增任意历史日期导航：首页仍沿用 90 天 K 线窗口，窗口外和未来日期受既有导航限制；没有把所有未来日期禁用，也没有增加新的历史截断规则。
- 写入失败不会保留半条记录，窗口可以修正后重试。若提示“记录已保存，但图表重算失败”，事实已提交且缓存待重算：关闭编辑并刷新首页，不要重复新增同一条记录；仅无变化保存不会代替刷新。
- 同日多次称重的 O/C 仍由首尾测量决定，H/L 仍按首尾锚定的能量轨迹计算，不保证包含中间测量极值。此次不改变体重模型。
- ml 不等于 g，混合单位食谱只能按比例；CUSTOM 单位只是该条记录的数量含义，不自动推断换算，不能通过替换来源把它改成 FOOD/RECIPE。
- 数据和备份仍未加密；无账号、云同步、自动健康平台接入或营养诊断。隐私和备份注意事项仍适用。

实现语义详见 [称重编辑说明](CAL37_WEIGHT_EDITING.md) 与 [历史饮食/运动修正说明](CAL38_HISTORICAL_RECORD_CORRECTIONS.md)。

## 数据在什么位置

默认主库：

```text
%LOCALAPPDATA%\CalorieK\data\caloriek.sqlite3
```

可把 `%LOCALAPPDATA%\CalorieK` 粘贴到资源管理器地址栏打开。`data\backups` 保存自动安全备份，`config.json` 保存设置页选择的目录偏好。程序解压目录不是数据目录，删除旧程序目录也不会自动删除默认用户数据。

数据目录优先级：命令行 `--data-dir` → 环境变量 `CALORIEK_DATA_DIR` → 保存的目录偏好 → 默认目录。高级用户可从 PowerShell 指定本次启动路径，例如：

```powershell
& "D:\Apps\CalorieK\CalorieK.exe" --data-dir "D:\CalorieKData"
```

持久切换目录请用设置页选择空目录并保存。程序复制数据库到新目录，保留原库；下次启动仍会优先采用现存命令行/环境变量覆盖，所以更改设置后应留意是否还有这些覆盖。

数据库、备份 ZIP 和导出 JSON 含有健康记录，目前不加密。请放在受保护的本机位置；应用不会自动上传或替你建立云端备份。

## 升级、schema v3 与恢复

- 更新程序前，先在设置页创建 ZIP 备份并保存到安全位置；关闭其他 CalorieK 实例，再解压新程序到独立文件夹运行。保留旧程序与备份，直到新版本验证完成。
- v0.0.3 → v0.0.4 继续使用 schema v3，不新增迁移、不改变能量单位或计算版本；应用版本号改变本身不会批量改写历史事实。备份/导出的 `app_version` 随创建它们的应用版本变化，恢复兼容性仍按实际 schema 校验。
- v0.0.1 使用 schema v2；v0.0.2 使用 schema v3，增量追加营养字段，不更改旧记录、能量、体重、时间戳、偏好或派生缓存。读取时复用已有兼容营养和历史快照，不回填历史。
- 有效 v2 库升级前生成 `data\backups\pre_migration_v2_to_v3_*.sqlite3`；v1 库先生成 `pre_migration_v1_to_v2_*.sqlite3`，沿用能量迁移后追加 v3。自定义数据目录的快照位于其 `backups` 下。
- 迁移前快照包括已提交的 WAL 内容，保持原 schema 和数据/单位，是独立 SQLite 文件。快照失败不执行迁移，迁移失败回滚并保留快照。再次打开不会重复升级或重复转换能量。
- 已用过旧 v0.0.2 的用户另有 CAL-12 启动修复：仅 FOOD/RECIPE、完整性标记为 0、四项新快照全空、至少一项旧快照大于零时，先保存 `backups\pre_repair_cal12_nutrition_*.sqlite3`，再将自身旧营养快照复制到新字段并标为完整。其余字段不变；全零、CUSTOM 和部分已有新快照的记录不修复。快照失败中止启动，写入失败回滚；无命中不备份、不写入。不增加版本或放宽一般未知语义。
- 比 schema v3 更新或结构损坏/不完整的数据库会被拒绝。不要强改 schema 标记；**v0.0.1 不应打开已升级的 v3 库**。需要回退时先停止使用并保留新数据，再依审核方案用升级前备份恢复，避免丢失升级后的记录。
- 设置页“从备份恢复”支持合法的 v1/v2/v3 **ZIP 备份**。在隔离候选库中完成迁移与校验，准备替换文件后为当前库创建 `backups\pre_restore_*.zip`，最后替换；源 ZIP 不变。其他程序占用数据库时可能安全失败；关闭其他实例后再处理。
- 恢复使用当前数据目录，不会自动采用 ZIP 中记录的原电脑路径。JSON 导出是查看/分析格式，当前没有 JSON 导入功能。
- 原始迁移快照 `.sqlite3` 不等于应用 ZIP 备份，不能直接通过 ZIP 恢复菜单使用。发生异常时保留整个数据目录、快照和错误信息，再按审核后的方案恢复；不要自行删除 WAL/SHM 或覆盖仍在使用的数据库。

## 每日营养

- 食品编辑器展示一组营养值；新食品未填写仍为未知，明确 `0.00` 为已知零。迁移前或内置食品可使用已有营养，包括零；显式 v3 数值优先。
- 新摄入保存当时快照；后来修改食品或食谱不改变历史。显示两位小数不会降低已保存或计算值的精度。
- 首页营养卡片可选择历史日期，仅影响营养卡片，不改变今天的能量和体重图表。
- 缺少任何摄入的营养数据时显示 **部分记录无营养数据**；数字只是已知部分合计。除上述获批的旧 v0.0.2 窄范围修复外，不回填历史；全部未知显示“未知”，无记录显示 `0.00 g` 并注明没有记录。
- ml 不等于 g。兼容体积食品沿用原 ml 基准比例；每 100g 元数据不能用于 ml 摄入，不猜测密度。
- 点击 K 线日期可查看按时间排序的饮食、运动和称重，并编辑选中的活动记录。普通份量修改缩放原快照；显式来源替换和手动总量修正的差别见上方 v0.0.4 功能说明。
- 仅切换手动模式、改变显示单位或只更正能量，不会顺便补全未改的 legacy 营养字段。显式改变营养向量时才保存用户选定的四项已知/未知状态；一般 `nutrition_complete=0` 的不完整含义不变。
- 仅记录和展示，不提供营养目标、评分或饮食建议。兼容性细节见 [CAL-12 交接说明](CAL12_IMPLEMENTATION.md)；历史实现交接记录不替代对应版本的最终发布验证证据。

## kJ、kcal 与模型

- 固定换算：`1 kcal = 4.184 kJ`。kJ 输入直接保存，kcal 输入先转换为 kJ；备份和 JSON 中的能量仍是 kJ，与当前显示偏好无关。
- 默认体重模型系数为 `32216.8 kJ/kg`，在 kcal 模式下显示等价的 `7700 kcal/kg`。模型是简化预测，不会把预测体重写入实际称重表。
- 运动能量应填写额外运动消耗（Active Calories），不是包含全天基础消耗的总热量，以免重复计入。
- 切换单位不会改变已存能量、模型结果或 Treemap 面积，也不会改变营养克数。营养不反推能量、不参与模型；沿用 CAL-6 的两位小数显示和精度保留控件。

## 启动或数据异常

- 找不到依赖或 DLL：先确认完整解压、没有单独移动 EXE，并核对 Release 的 Windows x64 要求；不要把网上零散 DLL 复制进程序目录。
- 找不到旧数据：检查设置页数据目录、`CALORIEK_DATA_DIR`、命令行参数及 `config.json`。不要把新的空库误认为旧库已被删除。
- 无法备份、迁移或恢复：保留完整错误信息，检查磁盘空间、目录写权限，以及是否有其他 CalorieK/SQLite 工具正在使用该库。
- 提交问题时说明 Windows 版本、程序版本（主窗口标题）和错误文本；截图与日志先去掉健康数据、姓名和个人路径。不要公开上传整个数据库、备份或 handoff ZIP。

## v0.0.4 及后续版本的发布流程（维护者）

每个目标版本/里程碑由其专用发布验证 issue 把关，v0.0.4 使用 CAL-41，不将 CAL-5、CAL-9 或其他历史 issue 作为永久发布关卡。工作流元数据见 [AGENTS.md](../AGENTS.md)：workspace `Atticum`、team `Atticumlos`、project `CalorieK`、issue prefix `CAL`、当前开发里程碑 `v0.0.4`。

1. Codex 在任务范围内修改源码/文档后停止，默认不执行测试、构建、发布或 Git 写操作。
2. 用户运行 `package_caloriek_handoff.bat`，交 ChatGPT 独立审核并生成任务专用 Windows BAT；用户执行后的结果是独立验证证据。
3. 本次版本/文档调整经审核和用户 Windows 验证通过后，才按明确授权提交，并从已确认的干净源码提交进入发布构建。重新核对 EXE/CLI/窗口版本为 `0.0.4`，保留 schema `3` 和原计算版本；旧版构建成功不能代替这一步。
4. 发布关卡还需核查隔离新库、旧 v0.0.3 合成数据/备份副本的升级使用、事实与偏好保留，执行完整 Windows 测试及打包 smoke。不得使用或上传私人真实数据。
5. 发布 ZIP 必须包含完整 one-folder 程序目录。检查 ZIP 内容、完整性和 SHA-256，并从新解压目录启动验证；仅在明确授权后创建 tag、push 和发布 GitHub Release。还需重新下载实际 Release 资产、核对哈希并 smoke，才算发布完成。

本轮仅更新源码元数据、版本断言和说明，不执行以上测试、构建、打包或发布步骤。审核 handoff 默认不带运行数据和历史验证结果；可用 `withresults`、经隐私确认的 `withdata`，或两者任意顺序组合。它不是用户可运行的 Windows Release ZIP。完整命令、排除规则、源码运行和构建入口见 [README](../README.md)。
